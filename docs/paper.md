# zeliji: 端末の多重化からエージェントの多重化へ
### 生TTYを捨てた協調エージェントワークスペースの設計と実装 (ドラフト v0.1)

## 概要

ターミナル多重化ツールは40年にわたり「1つの端末で複数の作業を扱う」問題を
解いてきたが、その前提は常に「ペインの中身は人間が操作する生の端末」であった。
LLMコーディングエージェント (Claude Code 等) の並列運用が一般化した2026年、
この前提は成立しなくなりつつある。エージェントの生TTY出力は人間にとって
ほぼノイズであり、必要なのは「誰が・何をして・誰が指示を待っているか」という
状態である。本稿では、端末エミュレーションを完全に排し、エージェントの
構造化イベントストリームを直接描画する協調ワークスペース zeliji の設計と
実装を報告する。zeliji は (1) 役割ごとの git worktree 隔離、(2) プレーン
ファイルによる共有タスクボードとメッセージング、(3) セル精度の自前ANSI
描画によるcockpit UI、(4) セッションIDの永続化による文脈込みの
detach/reattach を、Python 標準ライブラリのみ約1,900行で実現する。
日本語Windows実機でのフィールドテストにより、設計段階では発見不可能な
7件の障害を検出・修正した。

## 1. はじめに

複数のLLMエージェントを並列に走らせる開発様式が急速に普及している。
現行の主流は「git worktree でファイルを隔離し、tmux/zellij のペインに
エージェントを1つずつ置く」構成だが、これには2つの構造的問題がある。
第一に、**セッション間の状態共有が存在しない**。エージェント同士は互いの
作業を知らず、タスクの重複着手や統合時のコンフリクトが人間の目視監視に
委ねられる。第二に、**生TTYの表示が人間の監視帯域を超える**。数枚のペインに
流れるツールログの全文を追い続けることは現実的でなく、実際にzellij
コミュニティでは「入力待ちの検知」だけのための通知プラグイン群
(zellij-attention 等) が独立したカテゴリを形成している。

本研究の中心的な問いは次である: **多重化の単位を端末からエージェントに
引き上げたとき、ワークスペースはどう設計されるべきか。**

## 2. 関連ツールと歴史的文脈

### 2.1 多重化ツールの系譜

GNU screen (1987) の detach/reattach は「プロセスの寿命を端末の寿命から
切り離す」発明であり、以後40年間「永続するエンジン+着脱可能なビュー」
という構図は破られていない。tmux (2007) は全操作をコマンド言語として
外部化し、プラグイン生態系を生んだ。tmux のプラグイン群は本体が満たさな
かった欲求の目録として読める: tmux-resurrect (再起動を超える永続化)、
tmuxinator (宣言的セッション)、byobu (発見可能性)、wemux (権限差のある
共有)。これらは全て zellij (2021) で本体機能となった。一方、
dvtm+abduco の「関心の分離」による再構成は、合成コストをユーザーに
委ねたためニッチに留まり、iTerm2 の tmux control mode (2013) は
「エンジンが状態を所有し、ビューは通知プロトコルを購読して描画する」
分離の成功例となった。

### 2.2 エージェント並列運用ツール (2025-2026)

worktree 並列化CLI (claude-squad, uzi, gwq, dmux, workmux 等) は隔離を
提供するが協調機能を持たず、swarm 系 (claude-flow) は協調を持つが重厚で
ある。Anthropic 公式の Agent Teams (2026-02, 実験的) は共有タスクリストと
メッセージングを持つが、Claude 専用・内部状態・tmux 前提である。
2026年7月には「agent multiplexer」を称する製品群 (Herdr, Zentty 等) が
出現したが、いずれも「生TTYペイン+状態サイドバー」の構成であり、
エージェント間協調・worktree隔離・成果回収を統合するものはない。

### 2.3 zellij がまだ壊していない4つの前提

系譜分析から、zellij が保持したままの前提を4つ特定した:
(a) 操作主体は人間1人である、(b) ペインの中身は不透明なバイト列である、
(c) レイアウトは空間配置のみを宣言する、(d) 通知はステータスバー1行である。
zeliji はこの4前提の破壊を設計目標とする。

## 3. 設計

### 3.1 原則

1. **ファイルがUI** — 全状態はプレーンファイル。`cat` で見え、人間が直接
   編集でき、いかなるビューもファイルを読むだけで構築できる
2. **gitが真実** — 成果はブランチ、統合は merge。独自同期機構を持たない
3. **見れば分かる** — 全コマンド出力が次の一手を含む。キーヒント常時表示
4. **エージェント非依存** — 協調プロトコルは「ファイルを読みCLIを叩く」のみ
5. **常駐しない・依存しない** — デーモンなし、Python標準ライブラリのみ

### 3.2 破壊する前提への対応

| zellijの前提 | zelijiの再設計 |
|---|---|
| ペイン=生端末 | ペイン=エージェント。stream-json を直接描画し端末エミュレーション自体を排除 |
| 操作主体は人間1人 | 役割宣言 (zeliji.toml)+共有ボード+`tell` による外部操縦 |
| レイアウト=空間配置 | 宣言対象は仕事: 役割・担当パス・タスク依存 (`--after`) |
| 通知=1行 | 状態バッジ・`!`・端末ベル・タブタイトル (`zeliji ●2 ○1 ❗`) |

## 4. 実装

構成は5モジュール: bus (flock/msvcrt排他のタスクボード+メッセージング+
制御キュー)、team (worktree・役割チャーター・merge)、agentrun (claude を
`--output-format stream-json` で駆動するドライバ)、cockpit (セル精度の
行合成による自前ANSI描画)、term (VT有効化とキー入力の Win/Unix 抽象)。

特筆すべき実装判断:

- **detach/reattach の単位はプロセスでなく文脈**: 各役割のセッションIDを
  永続化し、`--resume` で会話の記憶ごと復帰する。cockpit の終了は
  デタッチであり、何も死なない
- **権限は3モード** (wemux の mirror/pair/rogue の再演): 既定の pair は
  worktree内編集+`zeliji`/`git` コマンドのみを許可し、全自動 (rogue) は
  明示オプトイン+画面バナー常時表示とする
- **外部制御** (`zeliji tell`): tmux send-keys に相当する操縦口。制御
  キューはバス上のファイルであり、エージェント自身も使用できるが、
  エージェント発の指示は送り主がタイムラインに明示される
- **人間向けタイムライン**: エージェントの発話は全文、ツール実行は
  1行に要約 (生ログは `v` で切替)。East Asian Width に基づくセル計算を
  自前で持ち、ANSI対応の最終クリップで「いかなる行も端末幅を超えない」
  ことを構造的に保証する

## 5. 評価

### 5.1 フィールドテスト

日本語Windows実機での実利用により、設計段階では発見不可能な障害を
7件検出・修正した: cp932 ロケールでのファイルI/Oクラッシュ、BOM付きTOML、
コンソール出力のエンコード例外、PDCurses の全角幅誤計算による表示崩壊
(→curses放棄の契機)、エージェント権限が共有バスに届かない問題、
`getch` による日本語入力の文字化け、未追跡ファイルによる worktree 回収
失敗。特に表示とエンコーディングの障害群は「日本語環境の非エンジニア」
という想定ユーザーでのテストなしには出現しなかった。

### 5.2 協調の実証

2つの実Claudeセッション (backend/frontend) が人間の介在なしに、
タスクclaim→実装→コミット→`task done`(依存解除)→関数シグネチャの
`say` 連絡→受信側の依存タスク着手→統合、を完遂した。また cockpit の
再起動を跨いで、前セッションで教示した合言葉を再開後のエージェントが
保持していることを確認した (文脈込み reattach の実証)。

### 5.3 UI の網羅検査

端末幅5種×表示状態7種×役割5、敵対的入力 (200字コマンド行、30件ボード、
極端な列幅重み) の全35ケースで、桁あふれ0・行あふれ0・例外0を確認した。

### 5.4 規模

実装は Python 約1,900行・外部依存0。tmux (~9万行C)、zellij (~10万行
Rust+wasm) に対し、端末エミュレーションの排除が規模差の主因である。

## 6. 考察と限界

「状態が見える多重化」は2026年7月時点で既に商品化競争に入っており
(Herdr等)、数ヶ月でコモディティ化すると予想される。持続的な差別化は
協調層 (ボード・依存・メッセージング・回収) と、生TTYを捨てたことで
可能になった人間側の帯域設計にあると考える。

限界: (1) 単一マシン・単一リポジトリ前提であり、リモート・複数閲覧者は
未対応 (read-only Web ビューをファイルUIの上に構築予定)。(2) 起動層は
claude CLI に依存する (協調層は非依存であり、他エージェントのドライバは
追加可能)。(3) `tell` はエージェント間の指示連鎖を許すため、送り主表示
以上の抑制 (レート制限・承認) は今後の課題。(4) 定性的ユーザー評価は
n=1 のフィールドテストに留まる。

## 7. 結論

多重化の単位を端末からエージェントへ引き上げると、端末エミュレーション
は不要になり、代わりに協調 (ボード・依存・権限) と監視帯域 (要約・通知・
トリアージ) が第一級の設計対象になる。40年の系譜の不変量「永続エンジン+
着脱ビュー」は、単位が変わっても有効であった — ただし永続化すべきものは
プロセスではなく文脈である。
