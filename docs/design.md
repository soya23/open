# zeliji 設計原則

先行する zellij のユースケースと競合調査 ([competitors.md](competitors.md))
から導いた、判断に迷ったとき立ち返る原則。

## 原則

1. **ファイルが UI** — 状態はすべて `.zeliji/` のプレーンファイル。
   `cat` で見え、人間が直接編集でき、壊れたら消せば直る。
   専用ビューアが要る状態を作らない。
2. **git が真実** — 成果はブランチ、統合は merge。zeliji が独自の
   同期機構を持たない。コンフリクトは「防ぐ」(worktree 隔離) と
   「早く見せる」(overlap 警告) だけで、解決は git に任せる。
3. **見れば分かる** (zellij の discoverability に倣う) — すべての
   コマンド出力は「次に何をすべきか」を含む。空のボードは
   追加コマンドの例を表示する。ヘルプを読まなくても回る。
4. **エージェント非依存** — 協調プロトコルは「ファイルを読む/CLI を叩く」
   だけ。Claude Code 前提の機能を協調層に入れない
   (チャーター注入だけが Claude 固有で、それも差し替え可能)。
5. **常駐しない・依存しない** — デーモンなし、サーバなし、
   Python 標準ライブラリのみ。watch ですら単なるループ。

## ユースケース (zellij 先行事例から)

1. **役割分担開発** — frontend / backend / reviewer を並列に走らせ、
   API スキーマ変更などの連絡は `say`、依頼は `task add --role` で。
   一番の想定シナリオ。
2. **見張り運用** — zellij コミュニティで AI エージェント監視プラグインが
   一大カテゴリ化している通り、「複数エージェントの状態を一目で見たい」
   は実需。watch ペイン+`status` の進捗表示が担う。
3. **散らかした後の片付け** — 並列化ツールの体験はマージで決まる
   (uzi/dmux の教訓)。`zeliji merge --cleanup` で収穫から掃除までを
   1コマンドに。

## 非目標

- 競争モード (同一タスク N 並列比較) — 将来の候補、今はやらない
- swarm 的メタオーケストレーション — claude-flow の機能過多が反面教師
- tmux 対応 — zellij ニッチに集中。レイアウト生成が薄い層なので
  必要になれば足せる
- タスクの階層・優先度・期限 — ボードが Jira 化したら負け。
  status / role / after の 3 つで止める
